> **Status**: Draft（骨架 —— 已定的写清，未定的标 `[待定]`；我的建议标 `[待确认]`）
> **Category**: Core · **Layer**: Foundation · **Priority**: T1
> **Depends On**: **A1**（元素表 schema + 参数 schema）· **A2**（化合物与步骤 schema + `schema_version`）
> **被依赖**: **0 个** —— **全项目第一个"终端系统"**（口径：`systems-index` 的 `Depends On` 列含 `A4` 的行数）
> **承担的角色**: 按索引的 Agent 列，它是**唯一的双 agent 指派**
> （`game-designer + godot-gdscript-specialist`）—— **它必须同时活在两侧。**
> **设计顺序**: 第 4 位

## Summary

**让"同一份 schema"在 Python 侧与 GDScript 侧不漂移**，
并**一次性解决**已散在 A1/A2/A3 三份 GDD 里的 **schema 版本迁移机制**。

## Overview

**它的形状与前三个系统本质不同**：
- **A1/A2 是数据**（元素、化合物、步骤）—— 被 8/2 个系统依赖。
- **A3 是算法**（把数据变成世界）—— 被 8 个系统依赖。
- **A4 是契约执行者** —— **被 0 个系统依赖**。

**为什么它是终端系统**：它不向任何运行时系统提供数据或算法，
它服务于**"数据与实现之间"**那层：**保证两侧对同一份 schema 的理解是一致的**。
所以它的"下游"不是系统，而是**开发流程本身**（以及 A1/A2 的数据能被两侧正确读入这件事）。

**三个承重来源（都不是本系统的自由）**：

| 来自 | 内容 |
|------|------|
| **Technical Risks #3** | **Python 与 GDScript 两侧各实现一遍校验，契约必然漂移** —— 这是本系统存在的理由 |
| **索引已给的倾向** | 「契约必须显式维护；**优先让一侧生成另一侧的期望值**」 |
| **A1 的契约** | **不得假设只有一侧解释器** |
| **A2 的契约** | **不得假设只有元素表需要版本化**；**不得假设表的形状不会变** |

**它必须交付的一件具体东西（跨系统欠账）**：
> **`schema 版本迁移机制`** —— 加 / 删 / 改字段时，**已存档的池与表怎么办**。
> 该项已被记在 **A1 · A2 · A3 三份 GDD 的 Open Questions 里**。
> **若不在此处一次性解决，它会长出三个不同的答案。**
> **这是 A4 的交付物之一，不是"顺带提到"。**

`[待定 —— 还要写：它在开发流程里的位置（何时跑、谁来跑、失败怎么办）·
它是否参与运行时（还是纯开发期工具）· 与 B16 存档（读旧档）的关系]`

## Player Fantasy

`[待定 —— 方向：A4 玩家看不见，但它的失败玩家【会】看见：
「百科说 A，游戏做 B」· 「编辑器里看着对，进游戏算出别的结果」。
所以它的玩家感受是【"两边算的是同一件事"】——
它是 A1 那条"信任"在另一个维度上的孪生：A1 保证"数字对得上"，A4 保证"两侧说的是同一套规则"。

反例：同一份数据在编辑期显示正常、在运行时行为不同 —— 而这比"报错"更糟，
因为它【看起来是对的】。]`

### States and Transitions

`[待定 —— 方向：A4 有两种状态维度，不要混为一谈：]`
- **schema 版本状态**（`v1` → 迁移中 → `v2`）—— 这是**全局**的
- **数据载入状态**（未校验 / 已校验 / 校验失败）—— 这是**每次载入**的

### Interactions with Other Systems

**上游 2 个（A1 · A2）** —— 注意本系统的 §Interactions 是**反向的**：
它不向任何下游承诺，而是**对上游提出要求**。

| 上游 | A4 从它读取什么 | **A4 不得假设** |
|------|-----------------|-----------------|
| **A1** | 元素表 schema · 参数 schema | 不得假设**只有一侧解释器**；不得假设**schema 不会变** |
| **A2** | 化合物与步骤 schema · `schema_version` | 不得假设**只有元素表需要版本化**；不得假设**表的形状不会变** |

**下游：无**（终端系统）。`[待确认 —— 是否真的没有下游？例如 B16 存档读旧档时是否要用迁移机制；
若是，那是"经由 A1/A2 的关系"还是"直接依赖"？需与索引核对]`

## Formulas

`[待定 —— 方向：]`
1. **契约校验判定式**：`两侧对同一份数据的解释结果 == 期望值`（必须能给出**具体哪一条**不符）。
2. **版本迁移映射**：`v_old → v_new` 的字段级映射（加/删/改三种情形各一套）。
3. **漂移检测**：两侧期望值的比对（**必须能失败** —— 一个"无论事实如何都通过"的检查不算检查）。

## Edge Cases

`[待定 —— 至少覆盖：字段被加 / 被删 / 被改名 · 默认值在两侧不一致 ·
旧档缺新字段 · 新档被旧解释器读到 · 迁移失败（部分迁移）· schema 版本号缺失 ·
两侧都"能跑"但结果不同（最难发现的一类）]`

## Dependencies

**上游 2 个**：A1 · A2。
**下游 0 个**（终端系统）—— 故本系统的"影响"不体现在依赖图上，而体现在
**它失败时 A1/A2 的数据会被两侧读成不同的东西**。

`[待定 —— 补两条由定位推出的性质：例如"它是唯一一个'失败对玩家不可见、但对正确性致命'的系统"·
"它的验收必须包含'一次故意的漂移注入'"]`

## Tuning Knobs

`[待定 —— A4 自身的可调项（例如校验的严格程度：警告 vs 拒绝）。
注意：schema 本身的形状属 A1/A2，A4 只校验与迁移 —— 不得另立。]`

## Acceptance Criteria

`[待定 —— 方向：]`
- **漂移注入测试**：**故意**在两侧造一个不一致 → 必须被检出（这是本系统最核心的验收项）
- **迁移往返测试**：`v1 → v2 → 读回` 后数据语义不变（值相等、类型正确）
- **同数据同结果测试**：同一份数据在 Python 与 GDScript 两侧的解释结果**逐一相同**
- **失败可定位测试**：校验失败时必须指出**具体哪一条**不符（不是"校验失败"四个字）
- **对称测试**：A2 已要求"不得假设只有元素表需要版本化" → **化合物与步骤的 schema 同样要被覆盖**

## Open Questions

- `[待定]` **权威在哪一侧**（schema 文件 / Python / GDScript）—— 本系统最核心的未定项
- `[待定]` **A4 是否参与运行时**，还是纯开发期工具？若参与，性能与失败策略都要重新考虑
- `[待定]` **是否真的没有下游**（B16 读旧档时是否直接依赖迁移机制？）
- `[待定]` **`schema 版本迁移机制`的具体形式** —— **这是 A4 必须交付的东西**（见 §Summary）
- `[待定]` **双 agent 的协作方式**（索引里 A4 是唯一的双 agent 指派）
