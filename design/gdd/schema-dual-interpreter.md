## Summary

**让"同一份 schema"在 Python 侧与 GDScript 侧不漂移**，
并**一次性解决**已散在 A1/A2/A3 三份 GDD 里的 **schema 版本迁移机制**。

## Overview

**它的形状与前三个系统本质不同**：
- **A1/A2 是数据**（元素、化合物、步骤）—— 被 8/2 个系统依赖。
- **A3 是算法**（把数据变成世界）—— 被 8 个系统依赖。
- **A4 是契约执行者** —— **被 0 个系统依赖**。

**为什么它是终端系统**：它不向任何运行时系统提供数据或算法，
它服务于**"数据与实现之间"**那层：**保证两侧对同一份 schema 的理解是一致的**。
所以它的"下游"不是系统，而是**开发流程本身**（以及 A1/A2 的数据能被两侧正确读入这件事）。

**三个承重来源（都不是本系统的自由）**：

| 来自 | 内容 |
|------|------|
| **Technical Risks #3** | **Python 与 GDScript 两侧各实现一遍校验，契约必然漂移** —— 这是本系统存在的理由 |
| **索引已给的倾向** | 「契约必须显式维护；**优先让一侧生成另一侧的期望值**」 |
| **A1 的契约** | **不得假设只有一侧解释器** |
| **A2 的契约** | **不得假设只有元素表需要版本化**；**不得假设表的形状不会变** |

**它必须交付的一件具体东西（跨系统欠账）**：
> **`schema 版本迁移机制`** —— 加 / 删 / 改字段时，**已存档的池与表怎么办**。
> 该项已被记在 **A1 · A2 · A3 三份 GDD 的 Open Questions 里**。
> **若不在此处一次性解决，它会长出三个不同的答案。**
> **这是 A4 的交付物之一，不是"顺带提到"。**

**它在开发流程里的位置**：**运行时只做轻量版本检查**（已定，见 §Core Rules ②）；
**完整校验在开发期做** —— 触发时机为「数据改动后」与「提交前」。
**为什么这样切**：完整校验的价值在于"在开发者手上拦住错误"，而不在于"在玩家机器上"。
把它放在运行时，等于**把开发期问题的代价推给玩家**（启动变慢），而拦住的东西本不该发生。

**与 B16 的接缝**：B16 读旧档时**调用 A4 定义的迁移机制**（机制归 A4、执行归 B16）。
**这也是本系统唯一的"下游"** —— 见 §Interactions。
它是否参与运行时（还是纯开发期工具）· 与 B16 存档（读旧档）的关系]`

## Player Fantasy
**这一层要给的感受**：**「两边算的是同一件事。」**

A4 玩家看不见，但**它的失败玩家会看见**：百科说 A、游戏做 B；编辑器里看着对、进游戏算出别的结果。
所以它是 A1 那条「**信任**」在另一个维度上的**孪生**：
**A1 保证"数字对得上"，A4 保证"两侧说的是同一套规则"。**

**反例**：同一份数据**在编辑期显示正常、在运行时行为不同**。
**这比"报错"更糟** —— 因为它**看起来是对的**，而错误会在很久之后、以"百科与行为不符"的形式浮出，
那时已经没人能把它和当初那个 schema 改动联系起来。

## Detailed Design

### Core Rules
| # | 规则 | 状态 | 依据 |
|---|------|------|------|
| ① | **单一真相源 = schema 文件本身**（YAML）。**两侧都从它生成期望值** —— 不让任何一侧的实现成为规范。 | ✅ 已定 | 用户拍板（见下方理由） |
| ② | **A4 参与运行时的方式 = 轻量版本检查**：版本不匹配 → **拒绝载入**。**完整校验离线做（开发期）**。 | ✅ 已定 | 用户拍板 |
| ③ | **迁移的职责切分**：**机制归 A4**（定义"怎么迁"），**执行归 B16**（读旧档时调它）→ **依赖图上 B16 增加一条指向 A4**。 | ✅ 已定 | 用户拍板 |
| ④ | **迁移是显式映射，不是通用魔法**：每一步 `vN → vN+1` 声明**字段级操作**（见下方迁移机制）。 | ✅ 已定 | 由 ① 推出：真相源显式，迁移也必须显式 |
| ⑤ | **迁移是链式的**：`v1 → v2 → v3`，**一次升一级、不跳级** —— 每步都小、可测。 | ✅ 已定 | 同上 |
| ⑥ | **失败即拒绝**：迁移失败 → **拒绝载入 + 指出是哪一步**（fail-fast，与全项目一致）。 | ✅ 已定 | 与 A1/A2/A3 的口径一致 |
| ⑦ | **版本号之外，还要有 schema 的【内容指纹】**：载入时既比版本号、**也比指纹**。指纹不符 → **拒绝载入**（即使版本号相同）。 | ✅ 已定 | §5a 自检发现的 F-A4-1，见下 |


### ⑦ 的理由（A4 最危险的那个洞）

**若 schema 被改了、但版本号忘了升** —— 版本检查会通过、迁移不会跑，
**数据就会被静默地按新 schema 解读。** 而这正是本项目最怕的失败形态：**看起来正常。**

所以：**版本号（人声明的意图）+ 内容指纹（数据自己的证据）必须同时比。**
**人可能忘，指纹不会。**

### ① 的理由（值得写下来）

**"schema 文件是权威"比"让一侧生成另一侧"更强**：后者会让**生成那一侧的实现成为事实上的规范** ——
于是**生成器里的一个 bug 就变成了规范**，而另一侧会"正确地"照着这个 bug 实现。
**真相源必须是数据（schema 文件），不是任何一侧的代码。**

### 🎯 迁移机制（A4 的交付物 —— 结掉 A1/A2/A3 三处共有的欠账）

**四个字段级原语**（迁移只能用这四个，不引入别的）：

| 原语 | 语义 | **必须显式声明的东西** |
|------|------|------------------------|
| **`add`** | 新增字段 | **默认值**（且默认值**写在 schema 文件里**，不写在迁移代码里 —— 否则又是两处定义） |
| **`remove`** | 删除字段 | ⚠️ **"它的信息去哪了"** —— 见下方警告 |
| **`rename`** | 改名 | 用 `add` + 迁值 + `remove` **表达**，不引入新机制 |
| **`transform`** | 值域变换（如单位改变） | **变换函数 + 往返校验**（变换后必须能读出原语义，否则就是有损） |

> ### ⚠️ 删字段是本机制里最危险的一个原语
>
> **若被删的字段承载了物质或状态，删掉它就等于丢失信息** —— 这是 P2 的边界。
> 所以 `remove` **必须显式声明"它的信息去哪了"**：丢弃？合并进别的字段？还是必须先一步 `transform`？
> **不能只是"删掉"** —— 那与"A1 里原子凭空消失"是同一类错误，只是发生在**时间维度**上。

### States and Transitions
**A4 有两种状态维度 —— 不要混为一谈**（这是本节要防的主要误解）：

| 维度 | 状态 | 作用域 |
|------|------|--------|
| **schema 版本状态** | `v1` → 迁移中 → `v2` → … | **全局**（整个数据集的 schema 走到哪一版） |
| **数据载入状态** | 未校验 → 已校验 / **校验失败** | **每次载入**（一份具体数据是否通过校验） |

**迁移**（见 §Core Rules ⑤ 链式）：
```
vN --(声明 vN->vN+1 的四原语)--> vN+1 --(继续)--> ... --> 目标版本
任一步失败 --> 拒绝载入 + 指出是哪一步（不得部分应用后继续）
```

**一条纪律**：**迁移必须是"全成或全不成"** ——
不允许"前三个字段迁好了、第四个失败"这种中间态被写回去
（那与 A3 的对账锁同源：**宁可拒绝，不可留下不可信的状态**）。

## Formulas
### ① 契约校验判定式

```
对 schema 中每条字段声明 f：
    两侧对同一份数据的解释结果(f)  ==  期望值(f)          ← 逐条比对，必须能指出【是哪一条】
```

### ② 迁移映射（链式）

```
vN -> vN+1  :=  [ 原语_1, 原语_2, ... ]     原语 ∈ { add, remove, rename, transform }
```
- `add(field, default)`：默认值**取自 schema 文件**，不写死在迁移代码里
- `remove(field, where_did_it_go)`：**必须声明信息去向**（丢弃 / 合并 / 先 transform）
- `rename`：用 `add` + 迁值 + `remove` **表达**，不引入新机制
- `transform(field, fn)`：**必须带往返校验**（有损变换不算通过）

### ③ 漂移检测（必须能失败）

```
两侧期望值比对 -> 全等则通过；否则列出【每一条】不符
```
> **本系统的验收必须包含"一次故意的漂移注入"** ——
> 因为**一个"无论事实如何都会通过"的检查不算检查**。
> （本会话已实测过这条纪律的价值：我自己的核对脚本出的假故障比被核对内容出的真缺陷还多。）

## Edge Cases
| 边界 | 行为 | 依据 |
|------|------|------|
| **字段被加** | 必须带默认值，且默认值取自 schema 文件 | §Formulas ② |
| **字段被删** | ⚠️ **必须声明"信息去哪了"**（丢弃 / 合并 / 先 transform）；不得只是删掉 | P2（信息不得凭空消失，只是发生在时间维度上） |
| **字段被改名** | 用 `add` + 迁值 + `remove` 表达 | §Formulas ② |
| **默认值在两侧不一致** | **检出并拒绝** —— 这正是"两侧各写一遍"最典型的漂移形态 | ① |
| **旧档缺新字段** | `add` 的默认值补上；**默认值来源必须唯一**（schema 文件） | ② |
| **新档被旧解释器读到** | **轻量版本检查拦住**（版本不匹配 → 拒绝载入） —— 这是运行时唯一把关的地方 | ② |
| **迁移到一半失败** | **拒绝载入 + 指出哪一步**；**不得写回中间态**（全成或全不成） | ⑥ + §States 纪律 |
| **schema 版本号缺失** | 拒绝载入（不得当成 `v1` 猜 —— 猜错会静默损坏数据） | ⑥ |
| **版本号相同但 schema 内容变了**（改了 schema 却忘了升版本号） | **指纹不符 → 拒绝载入** —— 这是本系统最危险的静默失败，只能靠内容指纹检出 | ⑦ |
| **⚠️ 两侧都"能跑"但结果不同** | **最难发现的一类**，也是本系统存在的理由：只能靠**漂移注入测试**与**同数据同结果测试**检出 | Technical Risks #3 |

## Dependencies
**上游 2 个**：A1 · A2。
**下游 1 个**：B16（见 §Interactions —— 本处不重复）。

### 两条由定位推出的性质

1. **它是唯一一个"失败对玩家不可见、但对正确性致命"的系统**。
   A1/A2/A3 的失败玩家都能看到（数字对不上 / 副产物异常 / 机器卡住），
   而 **A4 的失败在很长时间里表现为"看起来正常"** ——
   所以它的验收**不能依赖玩家反馈**，必须靠**主动注入漂移**。
2. **它的产物不是运行时数据，而是"开发期的一道闸"**。
   → 因此它的验收标准是**流程性的**（"改动后必跑"），而不是运行时的性能或行为指标。

## Tuning Knobs
### A4 自身的可调项

| 项 | 范围 | 默认（暂定） | 说明 |
|----|------|--------------|------|
| **校验失败的严格程度** | 警告 / 拒绝 | **拒绝** | 本文倾向"拒绝"（与全项目 fail-fast 一致）；"警告"会留下一份"有人看过的坏数据" |
| **漂移检测的触发时机** | 数据改动后 / 提交前 / 两者 | **两者** | 见 §Overview |

### 它**不**拥有的东西（边界）

> ⚠️ **schema 本身的形状属 A1/A2** —— 字段有哪些、类型是什么、范围多少，都不由 A4 决定。
> **A4 只做三件事：校验、迁移、检测漂移。**
> **不得在 A4 里"顺手"定义一个新字段** —— 那正是"同一事实两处定义"的入口。

## Acceptance Criteria
**六条，每条都可独立检验。**

| # | 验收项 | 通过标准 |
|---|--------|----------|
| **1** | **漂移注入测试**（核心） | **故意**在两侧造一个不一致 → **必须被检出**，且指出是**哪一条** |
| **2** | **同数据同结果测试** | 同一份数据在 Python 与 GDScript 两侧的解释结果**逐条相同** |
| **3** | **迁移往返测试** | `v1 → v2` 后数据语义不变（**值相等且类型正确** —— 同 A1 的序列化口径） |
| **4** | **迁移失败原子性测试** | 构造"第三步失败"的迁移 → **不得写回中间态**，必须拒绝载入并指出哪一步 |
| **5** | **对称覆盖测试** | A2 要求"不得假设只有元素表需要版本化" → **化合物与步骤的 schema 同样被校验与迁移覆盖** |

| **6** | **指纹漂移测试（F-A4-1）** | 改动 schema 内容但**不升版本号** → **必须被拒绝载入**（若只比版本号，这一条会漏过去） |

> **第 1 条是本系统最核心的验收项**，而且它有一个特殊性质：
> **测试对象是"检查器本身能否失败"** —— 这与其它系统的验收不同
> （A1 验的是"守恒对不对"，A4 验的是"**校验器抓不抓得住**"）。

### 🎯 而这次落地**改动了 A1 / A2 的两处**（都要如实记）

1. **`CompoundData.SCHEMA_VERSION` 这个常量被删掉了** ——
   它是"同一个事实的第二处定义"：真相源在 `contract.yaml`，版本号从那里经生成器出一道。
   两处各写一个 `1`，就可以各自悄悄改。
2. **`schema_version` 的默认值从 `SCHEMA_VERSION` 改成 `0`**，并给两张表都加了 `schema_fingerprint`。
   **这不是顺手改的**：Core Rule ⑦ 与 §Edge Cases 明写「版本号**缺失** → 拒绝载入（**不得当成 `v1` 猜**）」，
   而"默认值就是 `1`"**恰恰就是那个"猜 v1"的机制** —— 忘了在 `.tres` 里写版本号会被静默补成 v1。
   ⇒ `0` / `""` 是"**无版本**"的哨兵。
   **而落地时真的就撞上了这个洞**：`data/reactions.tres` 原先**根本没写** `schema_version`。

### 一处**切分**（为了不让依赖图成环）

「缺版本号」由 A1/A2 自己的 `validate()` 报（它们只管**缺没缺**）；
「版本号/指纹对不对」由 **`SchemaContract.check_head()`** 报 —— 而**它由【组装点】调用，不由 A1/A2 调用**。
理由：索引里 A4 依赖 A2（A4 校验的正是 A2 的表），**A2 再反过来引用 A4 的常量就成了环**。
这与「机制归 A4、执行归 B16」是**同一条切法**：机制归 A4，**调用归组装点**（当前组装点 = `t1_electrolysis.gd`）。

  ⚠️ **收到一个硬约束（本机实测，2026-10-03）**：**Godot 没有 YAML 支持** ——

  | 探针 | 结果 | 含义 |
  |------|------|------|
  | `ClassDB.class_exists("YAML")` | **false** | 引擎里根本没有 YAML 类 |
  | `JSON.parse_string("temperature: 60\n…")` | **`null`**（并报 Parse failed） | JSON 不是 YAML 的超集，喂不进去 |
  | `ConfigFile.parse(同一份 YAML)` | **err = 0（成功！）** ← ⚠️ | **这才是危险的那个** |

  **最后一行是本项目最怕的失败形态的又一个实例**：`ConfigFile` 是 INI 风格解析器，
  它会把 `temperature: 60` 当成一行键值、把 `- id: a` 当成**键名 `- id`** ——
  **它返回"成功"，而结构与 YAML 语义完全不同**（没有小节、列表被压平）。
  ⇒ **绝不能用 ConfigFile 去"读 YAML 然后当作读对了"。**

  **所以"两侧运行时直接读同一份 YAML"这条路要么给 GDScript 侧引入一个 YAML 依赖
  （与 Core Rule ②「运行时只做轻量版本检查」冲突），要么改成【开发期生成】。**
  **这是一处真决策点，尚未拍板 —— 它决定 A4 的文件布局，所以必须先定再写代码。**
