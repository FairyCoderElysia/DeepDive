## Summary

它是本项目的「**为什么**」的落点 ——
**而它的第一件事不是画界面，而是【定义上游要提供什么形状的归因】**。

## Overview

### 三条上游契约说的是同一句话（**而它们都没有定义那个记录的形状**）

| 来自 | 承诺给 B10 的 | **它不得假设** |
|------|---------------|----------------|
| **B2** | 每一条通道的**可读归因**（哪个旋钮 / 哪个接法） | 不得假设**失败可以事后重建** |
| **B5** | 灾难的**原因链**（从哪个条件偏移开始、经过哪些环节） | 同上 |
| **A3** | **可归因的失败**（哪个旋钮偏了、偏到哪一段） | 同上 |

> ### **→ 三处都说了"必须实时记录"，但三处都没有说【那个记录长什么样】。**
> **而 B10 是它的消费者 —— 所以这个形状必须由 B10 定义。**

### 概念文档给了它三问与一条硬条件

**三问**（line 207，原话）：
> **「灾难必须可诊断（【哪里堵了、为什么堵、哪一步放热失控】）。」**

**一条硬条件**（Risk #7，line 423，原话）：
> **「放大失败是否可诊断** —— 实验室跑通 ≠ 产线能跑（带宽 / 热量 / 压降 / 材料 / 停留时间）。
> **硬条件：放大失败必须可诊断**，否则**玩家会觉得被坑**。」**

**一条技术挑战**（line 403）：
> **「严谨度滑杆的规则引擎要可配置且可诊断（【能告诉玩家"为什么"】）。」**

### 而它面前有**六种"我的机器停了"**（这是前几轮攒出来的清单）

| # | 谁 | 为什么停 | 怎么恢复 |
|---|-----|----------|----------|
| 1 | **A3 对账锁** | 守恒失败 | 确认 + 重算基线 |
| 2 | **B2 结垢失效** | 慢性积垢到 100% | **清洗**（一段停机时间） |
| 3 | **A5 阻塞** | 产不出去（下游满 + 罐满） | 腾出容量 |
| 4 | **B5 灾难** | 失控（越界导致） | **修**（成本随严重度） |
| 5 | **C1 管路超限破裂** | 环境超限 | 换管 / 降压 |
| 6 | **A5 干涸** | 上游断供 | 接回上游 |

> **⚠️ 六种的【修法互不通用】** —— 所以"我的机器停了"这一句话**必须被拆成六句**，
> 否则玩家看到红灯却不知道该做什么。

### 边界（它不是什么）

- **不是归因的产生** —— 那是 **A3/B2/B5**（B10 **消费**归因，**不重建**它）。
- **不是 HUD 的布局** —— 那是 **B11**（B10 定义"要说什么"，B11 定义"放哪、长什么样"）。
- **不是热力图** —— 那是 **B12**。
- **不是百科** —— 那是 **B7**（B7 讲**事实**，B10 讲**这一台机器此刻怎么了**）。

**归因记录的字段集**：✅ 已定 —— **统一最小字段集 + 可扩展**（②，澄清 1）。

**六种停怎么组织**：✅ 已定 —— **按修法分组**（③，澄清 2）。

**推送还是可查**：✅ 已定 —— **分级**（④，澄清 3）。

**时间戳的单位**：✅ 已定 —— **游戏内时间**（澄清 4，F-B10-1）。

## Player Fantasy
**方向：**「**我知道出了什么事，我知道该动什么。**」

概念文档把它的反面写死了：**"不能是暗算"** ——
而**"暗算"的定义就是【玩家看着红灯、却无法把因果串起来】**。

**所以 B10 的幻想不是"信息丰富"，而是【因果可见】。**

**反例**：把六种原因全列出来。**那不是"玩家知道了原因"，那是"玩家面对一张更有信息量的红灯"** ——
**"哪里堵了、为什么堵、哪一步放热失控"这三问必须被逐条回答，而不是把原料摊开。**

## Detailed Design

### Core Rules
| # | 规则 | 状态 | 依据 |
|---|------|------|------|
| ① | **归因必须【实时记录】** —— **不得事后重建**。 | ✅ 已定 | 三条契约的同一句话 |
| ② | **B10 定义归因记录的【统一最小字段集】**（谁 · 哪个旋钮/接法/边 · 偏到哪一段 · 何时开始）+ **各系统可扩展**。 | ✅ 已定 | 用户拍板（见澄清 1） |
| ③ | **六种"停"按【修法】分组**；形式 = **现象 → 原因 → 修法**。 | ✅ 已定 | 用户拍板（见澄清 2） |
| ④ | **分级**：严重（灾难 / 失效 / 对账锁）→ **主动提示**；轻微（效率下降 / 接近上限）→ **可查**。 | ✅ 已定 | 用户拍板（见澄清 3） |
| ⑤ | **它必须能回答那三问**（哪里堵了 / 为什么堵 / 哪一步放热失控）。 | ✅ 已定 | 概念文档 line 207 |
| ⑥ | **放大失败必须可诊断**（带宽 / 热量 / 压降 / 材料 / 停留时间）。 | ✅ 已定 | **Risk #7 的硬条件** |

### 澄清 1：为什么是"**统一最小字段集**"而不是"各自自由"

**本项目已实测过 6 次**「同一事实两处定义、然后漂移」的事故（登记册的 `referenced_by` 纪律就是为此设的）。

> **而"归因的形状"正是一个会被三处各定义一次的东西** ——
> **三个上游都说了"必须记录"，谁都没定义。**
> **→ 若放任各自定义，B10 就要适配三套**，而第五套（未来的系统）会再加一套。

**最小集 = 四个字段**：

| 字段 | 它回答 |
|------|--------|
| **谁**（哪台机器 / 哪条边） | 三问里的"**哪里**" |
| **哪个旋钮 / 接法** | 三问里的"**为什么**" |
| **偏到哪一段** | "为什么"的程度 |
| **何时开始** | "为什么"的时间（**B19 的世界走慢会让"何时"变得重要**） |

> **而"哪一步放热失控"由 B5 的因果链【扩展字段】带** ——
> **最小集只保证三者能对齐，不替它们表达各自的专门性。**

### 澄清 2：为什么按【修法】分组 —— 而它与概念文档的三问**不冲突**

概念文档的**三问**是**诊断式**的（"**发生了什么**"）；
**而玩家的下一个动作是"我该做什么"。**

**→ 两者都需要，而顺序是固定的：【现象 → 原因 → 修法】。**

**六种"停"按它们的出路归档**：

| 修法 | 哪几种停 |
|------|----------|
| **确认 + 重算基线** | A3 对账锁 |
| **清洗**（一段停机） | B2 结垢失效 |
| **腾出容量** | A5 阻塞 |
| **修**（成本随严重度） | B5 灾难 |
| **换管 / 降压** | C1 管路超限破裂 |
| **接回上游** | A5 干涸 |

> **→ 在这里"按修法分组"与"按原因分组"恰好是一对一的**（六种停 = 六种修法）——
> **但标签不同：前者直接是玩家要的那个答案。**

### 澄清 3：为什么**分级**（重则推送、轻则可查）

| 约束 | 它要求 |
|------|--------|
| **本作是连续流、世界不停**（无时限、不暂停） | **主动推送不能打断玩家** |
| **B5 要求灾难"壮观" + "可诊断"** | **灾难必须被立即注意到** |

> **→ 分级是唯一同时满足两者的答案。**

**分界线**：**"玩家现在必须做什么"** ——
- **必须立刻做**（隔离 / 确认基线）→ **推送**；
- **可以等一下**（清洗 / 腾容量）→ **可查**。

### 澄清 4（F-B10-1）：归因的时间戳必须用**【游戏内时间】**

B19 已定：**超预算 → 世界走慢**（tick 变长），而**本作无时限**（所以那是合法的）。

**→ 而它给 B10 一个不显然的后果**：

| 用现实时间 | 用游戏内时间 ✅ |
|------------|-----------------|
| 同一段因果在走慢时会显示成"**持续了很久**" | 它显示的是**游戏内真的过了多久** |
| **在工厂很大、世界很慢时失真** —— 而那正是玩家最需要诊断的时候 | 一直准确 |

> **→ 最小字段集里的"何时开始"，单位必须是【游戏内时间】。**


### States and Transitions
| 诊断状态 | 含义 | 呈现方式 |
|----------|------|----------|
| **正常** | 无诊断 | 无 |
| **有警告** | 轻微（效率下降 / 接近上限） | **可查** |
| **有故障** | 严重（灾难 / 失效 / 对账锁） | **主动提示** |

**⚠️ 一条必须守住的**：**"主动提示"不等于"弹窗暂停"** ——
本作是连续流、世界不停，**所以推送必须是【不打断的】**（它出现在世界里的某处，而不是挡住世界）。

## Formulas
**B10 没有数值公式** —— 但它定义**一个数据结构**（这在本项目里是第一次）：

### 归因记录的【最小字段集】

```
归因 = {
    谁:      哪台机器 / 哪条边
    哪个:    旋钮 / 接法 / 通道
    偏到哪:  段 / 程度
    何时开始: 【游戏内时间】        ← 澄清 4（F-B10-1）
    ...扩展字段（各系统自己的）
}
```

### 它如何回答三问

| 问题 | 由谁回答 |
|------|----------|
| **哪里堵了** | `谁` |
| **为什么堵** | `哪个` + `偏到哪` |
| **哪一步放热失控** | **B5 的因果链（扩展字段）** |

### 呈现形式（**现象 → 原因 → 修法**）

```
现象  ->  原因（上面的字段）  ->  修法（六种之一）
```

## Edge Cases
| 边界 | 行为 | 依据 |
|------|------|------|
| **多个原因同时**（六种里的两种一起） | 允许；**按修法分组各列一条**（因为修法不同） | ③ |
| **原因在玩家看到之前就消失了** | `[待定]` —— 见 §Open Questions（是否保留历史） | —— |
| **玩家在巨慢的世界里收到诊断** | **时间戳仍准确**（用游戏内时间） | 澄清 4 |
| **世界走慢时推送的分级** | **不变**（分级按"必须立刻做什么"，不按现实时间紧迫感） | ④ |
| **归因记录是否进存档** | `[待定]` —— 若进，那是"复盘"能力；若不进，诊断只看当下 | §Open Questions |
| **上游没记归因** | **不允许发生** —— 三条契约都写明"不得假设可以事后重建" | ① |
| **信息过载**（六条同时弹） | **不允许** —— 按分级，只有"必须立刻做"的才推送 | ④ |

## Dependencies

**上游 3 个**：B2 · B5 · A3。
**下游 1 个**：见 §Interactions（**本处不重复** —— 同全项目纪律）。

### 两条由定位推出的性质

1. **它是本项目里第一个【定义数据结构】的系统。**
   别的系统定义的是**规则、公式、或世界形状** —— **而 B10 定义的是一个【字段集】**，
   且**上游必须按它来填**（因为它定义了"归因的形状"）。
   → **它是一个接口规范**，而它的正确性取决于**三处上游是否都愿意按同一形状记录。**
2. **它是"严谨是美感"的兑现处。**
   概念文档把这条支柱的全部说服力压在一句话上：**"不能是暗算"** ——
   而**暗算与否恰好是 B10 决定的**（不是 A3/B2/B5 决定的：它们只负责记录）。
   → **上游提供了原因，但"玩家能不能看懂"完全是 B10 的活。**

## Acceptance Criteria

**六条。**

| # | 验收项 | 通过标准 |
|---|--------|----------|
| **1** | **实时性测试** | 诊断**必须基于实时记录** —— **不得存在"事后重建"的路径** |
| **2** | **六种可分辨测试** | **六种"停"各自可辨**，且**各自给出对应的修法** |
| **3** | **三问测试** | 必须能逐条回答**哪里堵了 / 为什么堵 / 哪一步放热失控**（不是把原料摊开） |
| **4** | **不暗算测试** | 玩家看到红灯时**必须能查到原因**（不得只有现象） |
| **5** | **放大失败测试** | 产线跑不动的每一个物理原因（**带宽 / 热量 / 压降 / 材料 / 停留时间**）**都必须可归因** |
| **6** | **时间戳测试（F-B10-1）** | 归因的时间戳**必须是游戏内时间** —— 世界走慢时**不得失真** |
