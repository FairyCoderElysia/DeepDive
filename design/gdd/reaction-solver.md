## Summary

**把 A1 的原子池与 A2 的步骤表，变成"这一 tick 实际发生了什么"** ——
算限制试剂、推进反应、按条件分支决定产出与灾难，并把结果**以整数**写回池。

## Overview

**它在"数据 → 世界"这条线上的位置**：
`A1 元素（数据）` · `A2 化合物与步骤（数据）` → **`A3 求解（算法）`** → `A5 工艺图（图的物流）`。
**A1/A2 存事实，A3 让事实发生。**

**为什么它是第二根承重柱**：它**有 8 个直接依赖者**（与 A1 并列最多）。
其中 **A5 的一句话最能说明它的地位** ——
> 「A5 工艺图与连续流求解 —— depends on: A3（**图求值的语义来自求解器**）」

也就是说：**玩家连出来的工艺图，其"求值语义"不是 A5 自己定的，而是 A3 定的。**
A3 若把"多台机器争同一池料"的语义定歪了，A5 会把它放大到整张图上。

**三条来自上游的承重约束（已经定了，不是本系统的自由）**：

| 来自 | 约束 |
|------|------|
| **A1** | **不得产生分数原子** —— 必须走 A1 的余数累加器（`rate_scaled` 指数化整数 / `floor` / 误差有界） |
| **A1** | **不得假设对账失败还能继续** —— ⑤ 是"拒绝该动作 + 对账锁" |
| **A2** | **不得假设一个产物只有一条路径**；**不得假设条件只有"对/错"两态**（三段区间 + 分支） |

**边界（它不是什么）**：
- **不是数据** —— 元素属 A1、化合物与步骤表属 A2。
- **不是工艺图** —— 图上的物流顺序与连续流属 **A5**（A5 依赖 A3，不是 A3 依赖 A5）。
- **不是灾难本身** —— A3 **触发**灾难（`disaster` 标记），灾难的后果与连锁属 **B5**。
- **不是氧经济** —— A3 产生"耗了多少氧"这个事实，把它变成一个经济体属 **B4**。
- **不是参数面** —— A3 用参数、产生代价事实；"代价如何呈现"属 **A6**。

**求解粒度（已定，见 §Core Rules ①）**：A3 求解**一个步骤**、并**定义求值语义**；
**A5 用这套语义对整张图求值**。

**性能形状 —— 与 A1 是不同维度的预算**：
- A3 每次求解的规模是 **活跃机器数 × 每机输入项数**（**不是原子数**）；
- A1 的规模是 **原子数**（`TICK_ATOM_ORDER` = 万级原子/tick）。
- **两者是正交的两个维度** —— 机器很多但原子很少（许多空转机器）与机器很少但原子很多（大储罐流动），
  是两种不同的压力。**B19 必须分别预算，不能只留一份额度。**
- **A5 决定"哪些机器参与本 tick"**（图的活跃集），A3 只求解该集合内的层内联立。

**边界还剩的部分**：A3 与 A5 的接缝在"活跃集"上 —— 谁决定一个步骤本 tick 是否参与求解。
**本文的倾向：由 A5 决定参与集（它知道图的结构与连通性），A3 只负责该集合内的求解语义。**

## Player Fantasy
**这一层要给的感受**：**「我的设计真的在按化学跑。」**

A3 兑现的是**世界会照你写的规则运行**这个承诺。它不是"爽"也不是"紧张"，而是 **【可推演】**：

- **玩家改一个旋钮，能预见结果。**
- **遇到意外，能追到原因** —— 而不是"它就是这么发生了"。

**服务 P2（严谨是美感）**，并且与 P3 相接：**规则是你写的，A3 保证规则会被认真执行。**

**反例（要避免的感受）**：玩家调了旋钮但完全不知道会发生什么、也不知道为什么发生。
**那就是把 A3 变成了一台老虎机** —— 而老虎机与「严谨是美感」直接冲突。
**注意**：这个反例不是"太难"，而是"**不可推演**"。**难是可接受的，猜不是。**

## Detailed Design

### Core Rules
| # | 规则 | 状态 | 依据 |
|---|------|------|------|
| ① | **求解粒度（A3/A5 边界）**：A3 负责**一个步骤怎么求值**，并**定义**求值语义（含多机争料规则）；**A5 用这套语义对整张图求值**（拓扑顺序、连续流）。**语义只有这一处定义。** | ✅ 已定 | 用户拍板；与索引那句"A5 的图求值语义来自求解器"一致 |
| ② | **限制试剂**：对每条运行的步骤，`推进量 = min over 输入项 (可用量 ÷ 需求量)` —— 这是"谁先耗尽"。**分数推进由 A1 的余数累加器承担**（见 ③）。 | ✅ 已定 | A2 明确把限制试剂交给 A3 |
| ③ | **整数量化**：走 A1 的 `remainder_accumulator`（**每台机器、每种元素一个**；`rate_scaled` 指数化整数 / `floor` 舍入）。**A3 不得自创舍入方式。** | ✅ 已定 | A1 决策 ①（含实测依据） |
| ④ | **分支判定**：调 A2 的 `offset_to_branch_ratio`。**A3 只实现，不重新定义条件语义。** | ✅ 已定 | A2 决策 ③④ |
| ⑤ | **抢料 = 玩家可配优先级**：每台机器带一个**玩家可设的优先级**，高者先取料。**优先级是玩家创作的一部分（P3），不是内部随机数。** | ✅ 已定 | 用户拍板（见下方三条衍生要求） |
| ⑥ | **确定性**：同存档 + 同 tick 序列 → 结果**逐位一致**。**优先级机制天然满足** —— 顺序由数据决定，不由偶然决定。 | ✅ 已定 | A1 Edge Case C 的 (b) 口径 |
| ⑦ | **对账**：每 tick 结束后调 A1 的 `conservation_predicate`；失败 → **拒绝该动作 + 对账锁**。**不得夹住、不得静默。** | ✅ 已定 | A1 决策 ⑤ + 验收第 1 条 |
| ⑧ | **灾难**：条件越界 → 置 `disaster` 并**照常配平地**产出；**后果与连锁归 B5**。 | ✅ 已定 | A2 的 F-A2-3 澄清 |

### ⑤ 的三条衍生要求（**必须一起做，否则"优先级"是个半成品**）

1. **优先级必须可存档** —— 它是玩家设的，**丢了就等于玩家的创作丢了**。
2. **优先级必须可见** —— 否则玩家无法理解"我的机器为什么抢不到料"，
   而**不可解释的饥饿就是一则噪音**（B10 诊断的前提）。
3. **同优先级按需求比例等分**（用户已定）—— 完全确定、无隐藏变量，且**可解释**："同优先级 = 平分"是一句话能说清的规则。
   **两层语义各司其职：【不同优先级提供"抢"，同优先级提供"公平"的默认】。**

### ⑥ 的一个附带好处（值得写下来）

**"玩家可配优先级"比"轮转 + 种子"更强，不是更弱**：顺序**完全由存档数据决定**，
连种子都不需要；而且玩家改优先级能得到**可预期**的结果 —— 这正是 §Player Fantasy 要的"可推演"。
**代价**只是多一层 UI 与学习成本，而它与 P3「连出来的工艺属于玩家」同向。

### States and Transitions
**注意：这是"机器/步骤"的状态，与 A1 的"池"的状态是两套** —— 它们通过规则 ⑦ 相连
（输出池饱和会让机器进入"饱和"）。

| 状态 | 含义 | 进入 | 退出 |
|------|------|------|------|
| **空转** | 输入不足，**在制料与累加器继续保留** | 可用量 < 需求，或推进量为 0 | 够推进 |
| **运行** | 本 tick 有推进（可能是部分推进） | 推进量 > 0 | —— |
| **饱和** | 输出侧触到 A1 的池上限 | 输出元素饱和（A1 的 ①） | 下游消耗掉该元素 |
| **条件越界·灾难** | 某旋钮落在越界段 | 分支判定为越界（A2 的 ③） | 调回区间内 |
| **对账锁** | 守恒判定失败 | A1 的 `conservation_predicate` 失败 | 玩家确认「我知道了」+ 重算基线 |

**迁移**：
```
空转 --(输入到位)--> 运行 --(输出触顶)--> 饱和 --(下游消耗)--> 运行
任意态 --(某旋钮越界)--> 灾难 --(调回区间)--> 运行
任意态 --(守恒失败)--> 对账锁 --(玩家确认)--> 运行
```

**两条纪律**：
1. **所有状态都必须可复原**（同 A1 —— P5 无时限，不能有死档）。
2. **对账锁优先于灾难**：守恒失败意味着**状态本身不可信**，
   此时再跑灾难逻辑只会产出**不可信的灾难**。**先让玩家确认基线，再谈发生了什么。**

## Formulas
> **本节的原则：A3 的公式大多是【调用上游已登记的公式】，而不是新发明。**
> **凡是要新写的式子，都必须能被 A1 的守恒判定式接受。**

### ① 限制试剂与推进量

```
可推进份数 = min over 输入项 i ( 可用量_i ÷ 需求量_i )
推进       = 可推进份数        （分数；整数部分立即搬运，小数部分进累加器）
```
这是"**谁先耗尽**"的定义 —— 由比值最小的那一项限制。

### ② 同优先级等分（fair share）

```
对同优先级组 G 中的机器 m、输入项 i：
    分配比例 = 需求量(m,i) ÷ Σ_{m'∈G} 需求量(m',i)
```

> ⚠️ **实现要点（必须写清楚，否则会被写错）**：
> **等分必须"层内联立求解"，不能逐台分配。**
> 逐台分配的话，**先处理的机器会把份额吃掉** —— 结果将依赖处理顺序，
> 从而违反规则 ⑥（确定性）与"可推演"。
> **所以 A3 每 tick 的求解形状是【按优先级分层 → 层内联立 → 再流入下一层】，不是"逐机器循环"。**

### ②bis 完整求解过程（F-A3-1：把 ① 与 ② 组合成可执行的步骤）

**照原文实现时，必须按这个顺序 —— 否则"先分层还是先算 min"会变成实现者自己的编排：**

```
1. 按优先级分层（高 → 低）。这是【层间】的顺序，也是"抢料"唯一发生的地方。
2. 对当前层【迭代到不动点】（用户拍板；带迭代上限）：
     循环：
       a. 对每个输入项 i，按各机器的【当前实际需求_i】比例，把池中剩余可用量分给层内各机器
       b. 每台机器：推进量 = min over i ( 分到的量_i ÷ 需求_i )
       c. 若所有机器的推进量都不再变化 → 稳定，退出循环
       d. 否则：把【因其他输入受限而用不到的那部分份额】释放回池，回到 a
     若达到迭代上限仍未稳定 → 采用当前结果 + 【告警】（不得静默）
3. 本层稳定后：扣除输入、按 A2 算产出分支、按 A1 的累加器做整数量化、产出写回池，
   然后调 A1 的守恒判定式对账（失败 → 拒绝 + 对账锁）
4. 进入下一层（高优先级层用剩的，才轮到低优先级层）
```

> ### 为什么步骤 2 必须迭代（F-A3-2，用户拍板：迭代到不动点）
>
> **用"初始需求"分一趟会把用不到的料锁死。** 具体例子：
> 同一优先级两台机器，各要 `2H + 1O`；池里只有 **2H、100O** → H 是瓶颈，两台各只能推进 **0.5 份**。
> 但按初始需求比例分 O，它们会各分到 50 个 O，**而实际只需 0.5 个** →
> **99 个 O 被分出去却没人用，被白白锁住**；若此时还有第三台只要 O 的机器，**它会被饿死**。
> **玩家看到这一幕会认为系统算错了 —— 而它确实错了一半。**
>
> 所以：**"需求"应当是"它实际能推进的量所需要的量"，而那个量本身又依赖分配结果 → 这是个不动点。**
> 迭代让它收敛；`释放没用到的份额` 就是"把锁住的料还给池"。

### ③ 分支与产出占比

**不在此重定义** —— 用 A2 的 `offset_to_branch_ratio`（见 `design/registry/entities.yaml`）。

### ④ 产出的整数化

走 A1 的 `remainder_accumulator`（**每台机器、每种元素一个**）。

### ⑤ 对账

走 A1 的 `conservation_predicate`（整数比较、无容差）。

## Edge Cases
| 边界 | 行为 | 依据 |
|------|------|------|
| **输入不足** | **空转** —— 在制料与累加器**继续保留**，不消耗、不丢弃 | 规则 ② |
| **输入为 0** | 空转（同上） | ② |
| **多种输入同时耗尽** | 由 `min` 表达式**自然处理** —— 比值相同即同时耗尽，**无歧义**（不需要"平局"概念） | ① |
| **抢料被抢空** | 推进量 0 → 空转；**且必须可见**（否则不可解释的饥饿就是噪音） | ⑤ 衍生 2 |
| **条件恰好落在两段之间** | A2 的 `[a, b)`（左闭右开）约定**已给出归属**；运行时**仍需防御**该约定被破坏（否则行为未定义） | A2 的 `CONDITION_BAND_CONVENTION` |
| **灾难与对账锁同时发生** | **对账锁优先** —— 守恒失败意味着状态不可信，此时跑灾难逻辑只会产出不可信的灾难 | 见 §States 纪律 2 |
| **同一 tick 内机器的处理顺序** | **不是顺序问题** —— 按优先级分层、**层内联立**（见 §Formulas ②） | ⑤⑥ |
| **迭代达到上限仍未稳定** | **采用当前结果 + 告警**（不得静默）—— 与 A1 的"饱和 + 告警"同一做法 | 规则 ⑤（用户拍板） |
| **机器被拆除/停用** | ⚠️ **必须区分两样东西**（见下方） | P2 |

> ### ⚠️ 拆除机器时："进度"可以丢，"物质"不可以丢
>
> 这里有两样**性质完全不同**的东西，很容易被当成一件事处理：
>
> | 东西 | 是什么 | 拆除时 |
> |------|--------|--------|
> | **累加器 `r`** | 只是**进度**（"还差多少凑够一个原子"），**它不持有任何原子** | **可以丢弃** —— 丢的是进度，不是物质 |
> | **在制料**（已消耗进机器、尚未产出为产物的输入） | **是真实的物质**，只是暂时在机器里 | **必须退还到池**（或在玩家确认后销毁 —— 但那要按 A1 的`销毁`语义计价） |
>
> **若把在制料当作"进度"一起丢掉，就是物质凭空消失 —— 直接违反 P2。**
> 这是 A2 把"输入输出"定义成整份单位之后产生的必然结果：**部分批次意味着部分输入真的已经被取走了。**

## Dependencies
**上游 2 个**：A1 · A2。
**下游 8 个**：见 §Interactions（**本处不重复** —— 同 A1/A2 的纪律）。

### 两条由"它是算法"推出的性质（与 A1/A2 的"它是数据"相反）

1. **它不像 A1/A2 那样能在引擎外完整测试** —— A3 依赖 tick、顺序与跨机器的相互作用。
   **但它仍可做确定性测试**：给定固定的初始池 + 固定的机器集合 + 固定 tick 序列，
   **两次运行必须逐位一致**（见 §Acceptance Criteria 第 1 条）。
   **"可测"的标准从"纯函数"变成了"可复现"。**
2. **任何对 A3 的改动都要按"8 个下游会受影响"来评估** —— 而其中 **A5 最要紧**：
   求值语义一变，**整张图的求值结果全变**。

## Acceptance Criteria
**十条，每条都可独立检验。**

| # | 验收项 | 通过标准 |
|---|--------|----------|
| **1** | **确定性测试** | 同存档 + 同机器集合 + 同 tick 序列跑两遍 → **逐位一致**（含谁抢到料） |
| **2** | **限制试剂测试** | 构造"两种输入、其中一种先耗尽"→ **必须由正确的那一种限制推进** |
| **3** | **整数与累加器测试** | 任何产出都是**整数原子**；累加器残留恒 ∈ `[0, SCALE)` |
| **4** | **守恒测试** | 每 tick 通过 A1 的守恒判定（**整数比较、无容差**） |
| **5** | **对账拒绝测试** | 注入一次不守恒 → **必须拒绝该动作 + 进入对账锁**（不得夹住、不得静默） |
| **6** | **等分与顺序无关性测试** | 同优先级两机争同一输入 → 按需求比例分；**且打乱处理顺序后结果不变** |
| **7** | **分支可归因测试** | 副产物必须能回答"由哪个旋钮导致"（B10 的前提） |
| **8** | **灾难配平测试** | `disaster` 触发时产出**仍必须配平**（A2 的 F-A2-3） |
| **9** | **拆除退还测试** | 拆除一台有在制料的机器 → **在制料必须退还**（不得凭空消失） |

| **10** | **无浪费测试（F-A3-2）** | 构造"2 台机器争 H（共需 2H、各只需 0.5 份 O）、第 3 台只要 O"→ **O 不得被前两台锁死**，第三台必须能拿到 |

> **第 6 条是本系统最容易被实现错的一条** —— 逐台分配看起来更自然，但它会让结果依赖顺序，
> 从而违反第 1 条。**所以第 6 条不只是"分配正确"，它还必须是"与顺序无关"。**

## Visual/Audio Requirements
**A3 是算法层，无直接视听需求。**

但它是 **B5（灾难）**与 **B10（诊断）**的**信号源** —— 所以它必须**定义信号的形状**：

- **什么事件**：推进 / 空转 / 饱和 / 越界触发 / 对账锁 —— **这五种必须可区分**。
- **什么粒度**：每台机器？每个步骤？整条产线？（关系到 B10 能不能定位到"是哪台机器"）
- **必须包含归因信息**：哪个旋钮偏了、偏在哪一段（这是 B10 的前提，已在 §Interactions 承诺给 B10）。

> **边界**：A3 只负责**把这些事实暴露出去**；**怎么呈现（图标、音效、高亮）属 B5/B10/表现层。**
> 并沿用 `art-bible` §3④ 的纪律：**形状优先于颜色**（饱和度预算只给了氧气与危险）。

## Game Feel
**A3 不直接承担手感**（机器的启停节奏、视听反馈由 A5/A6 与表现层承担）。

但它提供**手感成立的前提：反馈的及时与可归因**。

- **改旋钮后必须能立刻看到差异** —— 否则"调参"这个核心动作就没有手感
  （玩家改了、看不到、只能猜）。这是一条**对 A3 的刷新延迟要求**。
- **同一台机器在不同优先级下的表现必须可预测** —— 否则玩家无法把"结果"归因到"我的设置"。
  （这正是规则 ⑤ 选择"玩家可配优先级"而非"轮转 + 种子"的原因：
  **玩家能理解自己设定的东西，但理解不了一个隐藏的轮转。**）

**反例**：玩家改了优先级、结果没变（或变化不可解释）→ 他会认为**这个功能是假的**。

## UI Requirements
**A3 不直接产出 UI** —— 它是 **B10（诊断）**与 **A6（参数与代价面）**的数据源。

它对 UI 的唯一义务是：**把"可归因的失败"以结构化形式暴露出去**（已在 §Interactions 承诺给 B10）：

- **哪台机器** · **哪个旋钮** · **偏在哪一段**（最优带 / 偏移带 / 越界）· **影响了什么产物**
- **为什么饥饿**（是输入不够，还是被高优先级的机器抢走了）—— **这一条尤其重要**，
  否则玩家无法区分"我设计错了"与"我优先级设低了"，而这两者的修法完全不同。

> **边界**：A3 保证**这些事实存在且可读**；**组织成给玩家看的文字与图形属 B10/A6。**
>
> **一条与 A1 一致的取向**（A1 §UI 已定）：**给可核对的细节，而不是给一个结论。**
> 例如不要只说「本机饥饿」，而要能回答「被谁抢走了多少」。
