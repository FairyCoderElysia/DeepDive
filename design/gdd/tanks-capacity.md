## Summary

定义**储罐能装多少、装的是什么、以及"装不下"时谁负责** ——
并承接概念文档那句**「产物必须立刻被下游或储罐接住」里的"储罐"那一半**。

## Overview

### 它的位置：**储罐是"收工"的标志物**

概念文档给核心循环的定义里，储罐是终点：
> **「一个"回合"＝把一条小工艺跑通并接到储罐上，让它在氧气预算内稳定运行」**

**所以储罐不只是个容器** —— 它是**"这条线跑通了"的物证**。
玩家把产线接到储罐上，标志着这条线从"试验"变成了"设施"。

### 三条约束（两条来自上游，一条来自概念文档）

**① 存贮不是免费的**（A1 给 B6 的契约）：
> Core Mechanics #6 的表：**占罐容 + 持续耗氧**。
> 且推论 2 明写：**「所以'先攒着以后再说'本身就是一个有代价的决定」**。

**② 储罐是"接不住"的最后一道防线**（Core Mechanics #4）：
> **「输入即刻变输出，产物必须立刻被下游或储罐接住」** ——
> **所以"下游与储罐都满"才是真正的阻塞**（A5 的规则 ⑤）。

**③ 三条接缝已经划好（不得越界）**：

| 谁 | 管什么 |
|----|--------|
| **B6（本系统）** | **装得下多少**（罐容上限、单位、装的是什么） |
| **B4 氧气经济** | **存贮的持续耗氧率**（它是速率，属 B4） |
| **A5 工艺图** | **"存不下时怎么办"** —— 走它的阻塞语义（上游阻塞 + 告警，绝不丢弃） |

### 边界（它不是什么）

- **不是原子池本身** —— 池的表示属 A1；B6 **在池之上**定义容器。
- **不是存贮的代价** —— 耗氧率属 B4。
- **不是阻塞语义** —— "接不住怎么办"属 A5。
- **不是纯度分级** —— 什么算"可用"属 B3（B6 只管装得下）。

**罐容随深度变化吗？** 倾向**不变** —— 罐子是玩家造的物件，深度影响的是**物流（C1）**，
不是罐子的容量。**但这需要与 C1 对齐**（列入 Open Questions）。

**罐子要耗材建造吗？** 属开放问题（B6 还是 C3）—— 见 §Core Rules ⑧。

**罐子会坏吗？** 概念文档把"管壁脆"归在 C1（深度），**不属 B6**。
罐子是否会坏（管壁脆那类机制在 C1）]`

## Player Fantasy
**方向：**「**我把它存下来了。**」

储罐给的是【资产的安心感】：产出来的东西有地方放，这条线不用一直盯着。
**但它同时是一个代价** —— 存着就要一直耗氧（推论 2）。

**这个张力就是 B6 的整个趣味所在：攒着是安全感，也是持续失血。**

**反例**：储罐只是"再多一个格子"。**那它就没有存在的理由** ——
把它换成"产能直接进下游"的无限缓冲也一样能跑，而那会**同时废掉两条已定的规则**
（占罐容 + 持续耗氧）。

## Detailed Design

### Core Rules
| # | 规则 | 状态 | 依据 |

| ① | **罐内表示 = 「化合物 → 数量」的表，不是元素池。** | ✅ 已定 | 见下方澄清 1（**这条不写清，存一次就会丢产物身份**） |
| ② | **罐容按【原子总数】计** —— 每个化合物组成确定，故原子总数可算。 | ✅ 已定 | 用户拍板 —— **不引入新量纲**（不要求 A2 补"分子体积"） |

| ⑧ | **罐子的建造成本**归谁（B6 还是 C3） | `[待确认]` | —— |

### 澄清 1：为什么罐子**不能**是元素池（① 的理由）

A1 的池记的是 `{元素: 数量}` —— **它不记化合物。**

**若罐子也这样做，那么"把水存进去、再取出来"就只剩氢氧原子、没有水了** ——
**存一次就把产物身份弄丢了。**

**这不是一个实现细节，而是本系统存在的理由**：A1 的池是"有哪些原子"的视角，
**而储罐必须持有"有哪些物质"的视角** —— 两者是**同一批物质的两个视图**，不能互相替代。

> **A1 的池与 B6 的罐的关系**：池是**全厂流动的原子**（供 A3 反应），
> 罐是**被收起来的物质**（供后续取用）。**物质进出罐时，在两种视图之间转换。**

### 澄清 2：取出规则（④ 的理由）

③ 允许混装之后，立刻产生一个问题：**一个装了 {水: 100, 氯: 20} 的罐子，取出来的是什么？**

**答案由 ①③ 直接推出：按组成比例取出（一股混合物流）。**

- **不需要让玩家选"取哪一种"** —— 那是把问题推给玩家；
- **也不需要"提纯"** —— 罐子不是分离器；
- **它直接变成下游要解决的问题**：要分开？**走 B3（纯度分级与分离提纯）**。

> **这条让"存贮"和"分离"接上了**：混装不是一种"省事"，而是一种**把今天的方便变成明天的工序**。
> 而这正是概念文档想要的取舍（"先攒着以后再说"本身有代价）。

### 澄清 3（F-B6-1）：**罐子 = 池的一个有界子集** —— 否则守恒会误报、工厂会锁死

A1 的守恒判定式是：
```
T_end(e) = 池(e) + 在途(e) + 机器内已整数量(e)     对比  T_start(e) + 净导入(e)
```
**它没有"罐内存量"这一项。** 而 B6 一落地，物质就会离开流动的池、进入罐子。

**若罐子被实现成"池之外的地方"，两个方向都会误报：**
- **存进去** → 池里的原子少了一批，而 `T_end` 里没有对应项 → **对账判定"不守恒"**
- **取出来** → 反过来 → **物质凭空出现**

**而 A1 的规则 ⑤ 是「对账失败 → 拒绝该动作 + 锁」** ——
**所以整个工厂会在玩家第一次存料时锁死。** 这比"算错"严重得多。

### 修法：**不需要改 A1 的公式，只需要明确一件事**

> ### **罐子 = 池的一个【有界子集】。**
> 它不是池之外的地方，而是池里"**被放在某个罐子里、并且有容量上限**"的那一部分。
> **于是"存入 / 取出"只是池内部的移动 → 守恒自动成立。**

**这条同时补上了 A1 契约里的一处不完整**：A1 承诺给 B6 的是"整数原子池"，
**但它没说过"罐子算不算池的一部分"** —— 已在 A1 的 §Interactions 里补一句，避免两处各说一套。

| 状态 | 含义 |
|------|------|
| **空** | 占用 = 0 |
| **部分** | 0 < 占用 < 罐容 |

## Formulas
### ① 罐容占用式（按原子总数）

```
占用(罐) = Σ_{罐内化合物 c} ( 数量(c) × 原子数(c) )        ← 每个化合物的组成确定，故可算
剩余容量  = 罐容 − 占用
```
**注意它是【跨化合物求和】** —— 这正是"允许混装"在数值上的含义。

### ② 取出（按组成比例）

```
取出 k 个原子时：
    对罐内每种化合物 c： 取出的数量(c) = k × ( 数量(c) / 占用(罐) )
    按 A1 的余数累加器整数量化（同 A3/A5 的纪律）
```
**罐内只有一种化合物时，这自然退化为"取出纯物质"** —— 不需要特例。

### ③ 剩余容量的用途

```
A5 的"接不住"判定要用它：若 下游可用容量 + Σ(罐的剩余容量) < 本 tick 想推出的量 -> 阻塞
```

## Edge Cases
| 边界 | 行为 | 依据 |
|------|------|------|
| **罐子满** | 占用 = 罐容 → **上游 A5 节点阻塞**（不是丢弃） | ⑤ + A5 规则 ⑤ |
| **罐子空** | 占用 = 0；取出量为 0（不是错误） | —— |
| **混装** | 允许；取出时**按组成比例**（见 §Formulas ②） | ①③ |
| **拆掉一个还有东西的罐子** | ⚠️ 里面的物质**必须退还到池**，不得凭空消失 —— **与 A3 拆机器时"在制料必须退还"是同一条纪律** | P2 + A3 的 §Edge Cases |
| **罐子被污染后装干净产物** | **不阻止** —— 污染会混进去，而**那正是"允许混装"的代价**（要分开就走 B3） | ①③ + B3 的接缝 |
| **多相共存**（水与油？） | **不建模**（本作不做相分离）—— 罐内只按"化合物 → 数量"记，不记物态 | 简化；如实标注 |
| **物质在池与罐之间来回移动** | 守恒**必须仍然成立**（F-B6-1：罐子是池的有界子集） | 澄清 3 |

## Acceptance Criteria

**五条，每条都可独立检验。**

| # | 验收项 | 通过标准 |
|---|--------|----------|
| **1** | **接住测试** | 下游满**且**罐满时，**必须阻塞上游**（不是丢弃）—— 与 A5 的验收 2 是同一件事的两侧 |

| **4** | **按比例取出测试** | 一个 `{A: 3, B: 1}` 的罐子取出 2 个原子 → 必须得到 `A:1.5, B:0.5` 的比例（整数量化后仍保持比例） |
| **5** | **非免费测试** | 罐内非空时**必须导致持续耗氧**（时间不推进则不再增长）—— 与 B4 的验收 5 对应 |

> **第 3 条是本文档存在的理由的可测形式**：
> 如果实现者把罐子做成元素池，第 3 条会失败 —— **而那正是最容易犯、也最隐蔽的错**（它在单次运行里看不出）。

## Game Feel

**方向：见 §Player Fantasy**（"存下来了"的安心感 vs "一直耗氧"的失血感）。

**它的手感是不对称的**：

**边界**：罐满/空的视听反馈可能属 **B15（音频）** —— B15 依赖 B1 与 B5，**需确认它在本系统上要什么**。

## UI Requirements

**B6 不直接产出 UI** —— 它是 **B11（HUD）**与 **B12（热力图）**的数据源。

它对 UI 的义务：
- **罐容占用率与余量**（供"还能接多少"的判断 —— 这是预判阻塞的前提）
- **混装时的组成**（"取出来会是混合物"要能事先知道）
- **与 B4 的协作读数**：罐内非空 → 持续耗氧（"我为什么在耗氧"要能追到这个罐子）

> 沿用全项目取向：**给可核对的细节，而不是给一个结论。**
> 例如不要只说「罐子满了」，而要能回答「**哪个罐、装了哪些东西、还能接多少**」。
