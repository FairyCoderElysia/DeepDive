## Summary

把"物质"表示成**可精确验证守恒的整数原子池**，并承载全项目共享的**元素表**、**参数 schema** 与**序列化契约**。

## Overview

**A1 是什么**：一个把"物质"表示成 **int64 原子池**的系统。池本体只回答一个问题：
**每种元素现在有多少个原子。** 它明确**不**回答"它们怎么反应"（属 A3），
也**不**回答"化合物是什么"（属 A2）。

**为什么必须是整数 —— 这条是实测出来的，不是偏好**（见 `docs/engine-reference/godot/VERSION.md` 追加实测之三/之四）：
`float` 是 64 位双精度且**不精确，却打印成"看起来对"的值**（`0.1 + 0.2` 打印 `0.3` 却不等于它）。
**浮点对账会把误差藏起来**，而 P2 是「严谨是美感」—— **守恒必须看得见，而且必须真的守**。
T0 时期已经因此误报过 **32 次假不守恒**（代数上完全守恒）。
代价是整数**溢出静默回绕**（`INT64_MAX + 1` 变负数，不报错），所以必须自己挡：**饱和 + 告警**。

### 三条已定的边界

1. **只管"有多少个原子"，不管"它们怎么反应"** —— 反应规则属 **A3 反应求解器**。
2. **只管元素，不管化合物** —— 化合物与反应数据表属 **A2**。
3. **参数 schema 寄居在本系统**（按评审批准的契约拆分）—— 因为 A3 要用参数、A6 要展示参数，
   若 schema 放在 A6 就会与 A3 成环。**"有哪些旋钮、范围、单位、默认值"下放到本系统的数据底座**，
   A6 只剩"表达代价面"。

### 典型 tick 量级 —— 从两个已知数推出来，不是拍的

| 侧 | 数 | 来源 |
|----|----|------|
| **规模** | 中等工厂 ≈ **10 份/秒** → **~167 原子/tick** | T0 定下的口径（1 份海水 = 1000 个原子） |
| **规模** | 大工厂 ≈ **1000 份/秒** → **~16,700 原子/tick** | ⚠️ **该量级是假设，待确认**（见下） |
| **成本** | 整数数组遍历 **≈ 32 ns/次** | 实测（100 万次累加 32 ms） |

**两者相乘**：16,700 个原子全池扫一遍 **≈ 0.54 ms**，在 60 fps 的 16.6 ms 预算里**绰绰有余**。

> **所以 A1 的设计基准是「万级原子 / tick」，不是百万级。**
> 这个数字直接交给 **B19（性能预算与管网 tick）** 当第一个性能预算 ——
> **这正是 A1 作为"先例"该产出的东西：一个被算出来、可被下游引用的基线。**

**⚠️ 一处必须标出来的空**：**大工厂量级（1000 份/秒）是假设，不是量出来的。**
它取决于飞船规模与玩家基地体量，而那两件事目前都还没定。
**如果这个假设错一个数量级，B19 的整个预算会跟着错一个数量级。** → 已列入 Open Questions。

## Player Fantasy

### 这一层要给玩家的感受

> **「这台机器算得对，而且我能自己验。」**

不是"爽"，也不是"紧张"。**A1 是基座，它的玩家感受是【信任】。**

而这个信任**不是靠"游戏说它对"** —— 是靠**玩家能自己验算**：

- 打开对账面板，投入与产出的原子数**逐元素对得上**，而且是**整数**对得上（不是"差不多"）
- 任何一个产物都能追溯：它是从哪些元素、经过哪几步来的
- 当系统**拒绝一次动作**时（对账失败），玩家看到的不是"出错了"，而是
  **"这一步会让原子凭空多出来，所以我不让它发生"**

### 它服务哪根支柱

**P2「严谨是美感灾难是内容」** —— 但这里有一层必须说清：
**严谨如果不可见，就只是"后台正确"。A1 的职责是把"后台正确"变成"前台可见且可验"。**

### 反例：要避免的那种感受

> 玩家看到界面上写着「守恒 ✅」，却**没有能力自己确认**。

**这和浮点对账的失败是同一件事**：**"看得见但不可验的对"，和"不对"没有区别。**

这不是修辞 —— T0 时期真的发生过：`0.1 + 0.2` **打印成 `0.3`**，界面看着是对的，
而它**并不等于** `0.3`（见 `docs/engine-reference/godot/VERSION.md` 追加实测之三）。

## Detailed Design

### Core Rules

七条决策中，**① 已定**，**②–⑦ 为实现建议待逐项确认**：

| # | 规则 | 状态 |
|---|------|------|
| ① | **原子计数 = int64 + 余数累加器**。池本体永远是整数；分数速率由每台机器自己的"余数累加器"累积，攒够 1 个原子才搬运一个整数。**溢出饱和 + 告警**（理由见下）。 | ✅ 已定 |
| ② | **元素种类 = 渐进**：海水 8 元素 + 矿脉按需新增（贴 P4「元素按来源分层」）。**前提：元素表 schema 必须版本化** —— 否则后期加元素要改所有下游。字段集 = 符号 / 名称 / 原子量 / 分类组（水·食盐·硬度·硫酸盐）/ 是否矿脉专属（P4 的钩子）。 | ✅ 已定 |
| ③ | **参数 schema 寄居本系统**：旋钮名 / 范围 / 单位 / 默认值。这是解开 A3 ↔ A6 循环的前提（评审批准的契约拆分）。 | ✅ 已定 |
| ④ | **显示口径 = 原子数**：内部与界面**同口径**，让玩家能直接验算。改动算成"份 / 分子"的方案、以及"两者都给"的折中**均被否**（界面克制优先，与 §4「同一画面最多两个信号色」同一条纪律）。典型 tick 量级见 §Overview。 | ✅ 已定 |
| ⑤ | **对账契约**：守恒**每 tick 可验**，且判定走**整数比较**（无浮点容差）；失败时**拒绝该动作 + 告警** —— 不夹住、不静默、不只记录。**理由**：另两种做法会把 P2 的「真的守」降级成「大致守」，而 P2 的整个卖点就是"真的守"。 | ✅ 已定 |
| ⑥ | **序列化契约**：**二进制**（`var_to_bytes` / `store_var`）+ 稀疏标记。**不得用 JSON** —— 实测 int64 过一遍 JSON 会掉精度，而 `==` 还会说它们相等。 | ✅ 已定 |
| ⑦ | **导入边界**：质量分数 → 原子数**只在导入时**发生；产物落进 `design/registry/entities.yaml` 的 `chem_elements`。 | ✅ 已定 |

**① 为什么必须是整数（实测，不是偏好）**：见 `docs/engine-reference/godot/VERSION.md` 追加实测之三/之四 ——
- `int` 是 64 位，但**溢出静默回绕**（`INT64_MAX + 1` 变负数，不报错）→ 所以必须自己挡。
- `float` 是 64 位双精度且**不精确，却打印成"看起来对"的值**（`0.1+0.2` 打印 `0.3` 却不等于它）→
  **浮点对账会把误差藏起来**，直接击穿 P2「严谨是美感」。T0 时期已因此误报过 **32 次假不守恒**。

### States and Transitions

这些状态是**从上面七条规则推出来的**，不是另起一套：

| 状态 | 由哪条规则推出 | 行为 |
|------|----------------|------|
| **正常** | 默认 | 计数 ≥ 0；原子可增可减 |
| **导入中** | ⑦ 换算只在导入时 | **唯一允许做"质量分数 → 原子数"换算的时刻**；结束后内核只认原子数 |
| **稀疏** | ② 渐进元素集 | **表示态**（不是独立运行时状态）：只存出现过的元素。必须写明 —— 否则实现者会纠结"缺的元素是 0 还是不存在" |
| **饱和** | ① 溢出静默回绕 | 某元素触顶 → **拒绝再增该元素 + 告警**（不回绕、绝不允许负值） |
| **对账锁** | ⑤ 拒绝动作 + 告警 | 出现会被判定不守恒的动作 → **拒绝它**，并进入需要玩家确认的状态 |
| **快照只读** | ⑥ 序列化契约 | 存档 / 读档期间**禁止变更**，保证快照一致 |

**迁移**：

```
正常  --(载入外部配方)-->  导入中  --(换算完成)-->  正常
正常  --(某元素触顶)---->  饱和    --(玩家消耗掉该元素)-->  正常
正常  --(一次会被判定不守恒的动作被拒绝)-->  对账锁  --(玩家确认「我知道了」+ 重算基线)-->  正常
任意态  <--(存档 / 读档)-->  快照只读  --(完成)-->  回到原态
```

**纪律一：所有状态都必须可复原。** 因为 **P5 是无时限** —— 不能存在"死档"。
对账锁也必须能靠**一次确认**走出来，而不是永久卡住。

**纪律二：对账锁的解释必须是"化学的"，不是"程序的"。**
玩家看到的不能是"内部错误"，而要是 ——
**「这一步会让原子凭空多出来，所以我不让它发生。」**
（这正是 §B 里那句承诺的落地。）

> ⚠️ **一处尚未定的**：**对账锁该多严？** 本文写的是"出现一次就锁"，但这可能过严：
> 一次边界舍入就可能触发，会让玩家频繁被打断。备选是"连续 N 次 / 单位时间超过阈值才锁"。
> **本文暂按"出现即锁"写，理由是它可验且玩家能理解；但阈值应在 T1 用真实数据再定。** → 见 Open Questions。

## Formulas

`[待定 —— 至少要有这三条]`

1. **质量分数 → 原子数（只在导入时）**：[已实测] 元素 `e` 的原子数占比 = `(质量分数_e ÷ 原子量_e) / Σ(质量分数_i ÷ 原子量_i)`。
   海水实测：换算后 **H:O = 2.0006**（≈水的 2:1）；若直接当原子数用则 **H:O = 0.126 → 海水造不出水**。

## Acceptance Criteria

`[待定 —— 每条必须可独立检验，不能是"运行正常""感觉对"]`
草案方向：
- 任意一条已知工艺流程，**每 tick 原子总数恒定**，且判定走**整数比较**（无容差）
- **溢出注入测试**：人造一次溢出，必须得到**饱和 + 告警**，不得出现负值
- **序列化往返测试**：池 → 存 → 读 → 池，**值相等且 `typeof()` 仍是 `INT`**
  （依据实测：JSON 往返会掉精度**且 `==` 会说谎**，所以必须同时断言类型）
- 海水导入：**H:O 原子比 ∈ [2.0000, 2.0012]**（实测 2.0006）

## Open Questions

- ⚠️ **大工厂量级（1000 份/秒）是假设，不是实测** —— 它决定"万级原子 / tick"这个基准，而该基准直接决定 B19 的性能预算。**需在飞船规模与玩家基地体量定下来之后复核**（若错一个数量级，B19 的预算全错一个数量级）。
- ✅ **已决**：元素种类 = **渐进**（海水 8 元素 + 矿脉按需新增）—— 见 §Core Rules ②
- ✅ **已决**：参数 schema **必须版本化**（这是 ② 的前提）—— 但**版本迁移的具体机制**仍未定，见下
- ⚠️ **对账锁该多严**：本文暂按"出现即锁"写；备选是"连续 N 次 / 单位时间超阈值才锁"。**阈值应在 T1 用真实数据再定**（见 §States and Transitions 末尾）
