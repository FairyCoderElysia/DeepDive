## Summary

把"物质"表示成**可精确验证守恒的整数原子池**，并承载全项目共享的**元素表**、**参数 schema** 与**序列化契约**。

## Overview

**A1 是什么**：一个把"物质"表示成 **int64 原子池**的系统。池本体只回答一个问题：
**每种元素现在有多少个原子。** 它明确**不**回答"它们怎么反应"（属 A3），
也**不**回答"化合物是什么"（属 A2）。

**为什么必须是整数 —— 这条是实测出来的，不是偏好**（见 `docs/engine-reference/godot/VERSION.md` 追加实测之三/之四）：
`float` 是 64 位双精度且**不精确，却打印成"看起来对"的值**（`0.1 + 0.2` 打印 `0.3` 却不等于它）。
**浮点对账会把误差藏起来**，而 P2 是「严谨是美感」—— **守恒必须看得见，而且必须真的守**。
T0 时期已经因此误报过 **32 次假不守恒**（代数上完全守恒）。
代价是整数**溢出静默回绕**（`INT64_MAX + 1` 变负数，不报错），所以必须自己挡：**饱和 + 告警**。

### 三条已定的边界

1. **只管"有多少个原子"，不管"它们怎么反应"** —— 反应规则属 **A3 反应求解器**。
2. **只管元素，不管化合物** —— 化合物与反应数据表属 **A2**。
3. **参数 schema 寄居在本系统**（按评审批准的契约拆分）—— 因为 A3 要用参数、A6 要展示参数，
   若 schema 放在 A6 就会与 A3 成环。**"有哪些旋钮、范围、单位、默认值"下放到本系统的数据底座**，
   A6 只剩"表达代价面"。

### 典型 tick 量级 —— 从两个已知数推出来，不是拍的

| 侧 | 数 | 来源 |
|----|----|------|
| **规模** | 中等工厂 ≈ **10 份/秒** → **~167 原子/tick** | T0 定下的口径（1 份海水 = 1000 个原子） |
| **规模** | 大工厂 ≈ **1000 份/秒** → **~16,700 原子/tick** | ⚠️ **该量级是假设，待确认**（见下） |
| **成本** | 整数数组遍历 **≈ 32 ns/次** | 实测（100 万次累加 32 ms） |

**两者相乘**：16,700 个原子全池扫一遍 **≈ 0.54 ms**，在 60 fps 的 16.6 ms 预算里**绰绰有余**。

> **所以 A1 的设计基准是「万级原子 / tick」，不是百万级。**
> 这个数字直接交给 **B19（性能预算与管网 tick）** 当第一个性能预算 ——
> **这正是 A1 作为"先例"该产出的东西：一个被算出来、可被下游引用的基线。**

**⚠️ 一处必须标出来的空**：**大工厂量级（1000 份/秒）是假设，不是量出来的。**
它取决于飞船规模与玩家基地体量，而那两件事目前都还没定。
**如果这个假设错一个数量级，B19 的整个预算会跟着错一个数量级。** → 已列入 Open Questions。

## Player Fantasy

### 这一层要给玩家的感受

> **「这台机器算得对，而且我能自己验。」**

不是"爽"，也不是"紧张"。**A1 是基座，它的玩家感受是【信任】。**

而这个信任**不是靠"游戏说它对"** —— 是靠**玩家能自己验算**：

- 打开对账面板，投入与产出的原子数**逐元素对得上**，而且是**整数**对得上（不是"差不多"）
- 任何一个产物都能追溯：它是从哪些元素、经过哪几步来的
- 当系统**拒绝一次动作**时（对账失败），玩家看到的不是"出错了"，而是
  **"这一步会让原子凭空多出来，所以我不让它发生"**

### 它服务哪根支柱

**P2「严谨是美感灾难是内容」** —— 但这里有一层必须说清：
**严谨如果不可见，就只是"后台正确"。A1 的职责是把"后台正确"变成"前台可见且可验"。**

### 反例：要避免的那种感受

> 玩家看到界面上写着「守恒 ✅」，却**没有能力自己确认**。

**这和浮点对账的失败是同一件事**：**"看得见但不可验的对"，和"不对"没有区别。**

这不是修辞 —— T0 时期真的发生过：`0.1 + 0.2` **打印成 `0.3`**，界面看着是对的，
而它**并不等于** `0.3`（见 `docs/engine-reference/godot/VERSION.md` 追加实测之三）。

## Detailed Design

### Core Rules

七条决策中，**① 已定**，**②–⑦ 为实现建议待逐项确认**：

| # | 规则 | 状态 |
|---|------|------|
| ① | **原子计数 = int64 + 余数累加器**。池本体永远是整数；分数速率由每台机器自己的"余数累加器"累积，攒够 1 个原子才搬运一个整数。**溢出饱和 + 告警**，且**饱和时上游阻塞**（见 §Edge Cases —— **绝不丢弃**：丢弃等于物质凭空消失、直接违反 P2）。 | ✅ 已定 |
| ② | **元素种类 = 渐进**：海水 8 元素 + 矿脉按需新增（贴 P4「元素按来源分层」）。**前提：元素表 schema 必须版本化** —— 否则后期加元素要改所有下游。字段集 = 符号 / 名称 / 原子量 / 分类组（水·食盐·硬度·硫酸盐）/ 是否矿脉专属（P4 的钩子）。 | ✅ 已定 |
| ③ | **参数 schema 寄居本系统**：旋钮名 / 范围 / 单位 / 默认值。这是解开 A3 ↔ A6 循环的前提（评审批准的契约拆分）。 | ✅ 已定 |
| ④ | **显示口径 = 原子数**：内部与界面**同口径**，让玩家能直接验算。改动算成"份 / 分子"的方案、以及"两者都给"的折中**均被否**（界面克制优先，与 §4「同一画面最多两个信号色」同一条纪律）。典型 tick 量级见 §Overview。 | ✅ 已定 |
| ⑤ | **对账契约**：守恒**每 tick 可验**，且判定走**整数比较**（无浮点容差）；失败时**拒绝该动作 + 告警** —— 不夹住、不静默、不只记录。**理由**：另两种做法会把 P2 的「真的守」降级成「大致守」，而 P2 的整个卖点就是"真的守"。 | ✅ 已定 |
| ⑥ | **序列化契约**：**二进制**（`var_to_bytes` / `store_var`）+ 稀疏标记。**不得用 JSON** —— 实测 int64 过一遍 JSON 会掉精度，而 `==` 还会说它们相等。 | ✅ 已定 |
| ⑦ | **导入边界**：质量分数 → 原子数**只在导入时**发生；产物落进 `design/registry/entities.yaml` 的 `chem_elements`。 | ✅ 已定 |

**① 为什么必须是整数（实测，不是偏好）**：见 `docs/engine-reference/godot/VERSION.md` 追加实测之三/之四 ——
- `int` 是 64 位，但**溢出静默回绕**（`INT64_MAX + 1` 变负数，不报错）→ 所以必须自己挡。
- `float` 是 64 位双精度且**不精确，却打印成"看起来对"的值**（`0.1+0.2` 打印 `0.3` 却不等于它）→
  **浮点对账会把误差藏起来**，直接击穿 P2「严谨是美感」。T0 时期已因此误报过 **32 次假不守恒**。

### States and Transitions

这些状态是**从上面七条规则推出来的**，不是另起一套：

| 状态 | 由哪条规则推出 | 行为 |
|------|----------------|------|
| **正常** | 默认 | 计数 ≥ 0；原子可增可减 |
| **导入中** | ⑦ 换算只在导入时 | **唯一允许做"质量分数 → 原子数"换算的时刻**；结束后内核只认原子数 |
| **稀疏** | ② 渐进元素集 | **表示态**（不是独立运行时状态）：只存出现过的元素。必须写明 —— 否则实现者会纠结"缺的元素是 0 还是不存在" |
| **饱和** | ① 溢出静默回绕 | 某元素触顶 → **拒绝再增该元素 + 告警**（不回绕、绝不允许负值） |
| **对账锁** | ⑤ 拒绝动作 + 告警 | 出现会被判定不守恒的动作 → **拒绝它**，并进入需要玩家确认的状态。**"一次" = 一个 tick 内的一次搬运动作**（可被拒绝的最小单位） |
| **快照只读** | ⑥ 序列化契约 | 存档 / 读档期间**禁止变更**，保证快照一致 |

**迁移**：

```
正常  --(载入外部配方)-->  导入中  --(换算完成)-->  正常
正常  --(某元素触顶)---->  饱和    --(玩家消耗掉该元素)-->  正常
正常  --(一次会被判定不守恒的动作被拒绝)-->  对账锁  --(玩家确认「我知道了」+ 重算基线)-->  正常
任意态  <--(存档 / 读档)-->  快照只读  --(完成)-->  回到原态
```

**纪律一：所有状态都必须可复原。** 因为 **P5 是无时限** —— 不能存在"死档"。
对账锁也必须能靠**一次确认**走出来，而不是永久卡住。

**纪律二：对账锁的解释必须是"化学的"，不是"程序的"。**
玩家看到的不能是"内部错误"，而要是 ——
**「这一步会让原子凭空多出来，所以我不让它发生。」**
（这正是 §B 里那句承诺的落地。）

> ⚠️ **一处尚未定的**：**对账锁该多严？** 本文写的是"出现一次就锁"，但这可能过严：
> 一次边界舍入就可能触发，会让玩家频繁被打断。备选是"连续 N 次 / 单位时间超过阈值才锁"。
> **本文暂按"出现即锁"写，理由是它可验且玩家能理解；但阈值应在 T1 用真实数据再定。** → 见 Open Questions。

## Formulas

### ① 质量分数 → 原子数（**只在导入时**发生）

```
原子数占比(e) = (质量分数(e) ÷ 原子量(e)) / Σ (质量分数(i) ÷ 原子量(i))
```

**校验值（已实测）**：海水换算后 **H:O = 2.0006**（≈ 水的 2:1，反证主体确实是水）；
若**直接**把质量分数当原子数用，则 **H:O = 0.126 → 海水造不出水**。

### ② 余数累加器 —— 关键是把它**也整数化**

朴素的"每台机器存一个 `float` 余数"会把**浮点问题从池里请回来**（存进存档更糟）。
所以累加器用**放大整数**：

```
SCALE = 2^20 (= 1,048,576)
每台机器 m、每种元素 e 持有一个余数 r[m][e] ∈ [0, SCALE)

每 tick：
  -- 速率的表示：rate_scaled 的单位是「原子 × SCALE / tick」，本身即整数
  -- （绝不用 float 速率 × SCALE —— 那一步会把浮点请回来，正是决策 ① 要根除的）
  需求 d = rate_scaled        ← 直接相加，全程无浮点乘法
  r[m][e] += d
  n = r[m][e] / SCALE          ← 整数除法，即 floor
  r[m][e] -= n × SCALE
  搬运 n 个原子（n 为整数）
```

**全程整数运算 → 无浮点漂移 → 可被 ⑥ 的二进制契约精确存档**（与决策 ⑥ 闭合）。

**舍入方向必须是 `floor`（向下）**：因为 `r ≥ 0` 恒成立 ⇒ `r ∈ [0, SCALE)`；
且 **floor 只会少搬、绝不超搬** ⇒ **池永远不会凭空多出原子**。

**误差上界（有界，不漂移）**：

> **池相对"理想连续模型"的偏差 < 机器数 × 元素种数 个原子。**

因为每个 `(机器, 元素)` 对最多欠一个原子。**这是有界误差，不是累积漂移** ——
这正是整数方案与浮点方案的**本质差别**。

> ### 复核记录（2026-10-03 · Godot **4.7.2** · 真实引擎，非纸面推导）
>
> | 复核项 | 实测 |
> |--------|------|
> | `int64` 溢出行为 | `9223372036854775807 + 1 = -9223372036854775808` —— **静默回绕，引擎不报错** ⇒ **① 的"溢出饱和 + 告警"是必需的**，否则会静默变成负物质 |
> | `JSON` 过 int64 | `9007199254740993` → `9007199254740992.0`，**且 `typeof()` 从 `INT(2)` 变成 `FLOAT(3)`**；**而 `==` 仍然返回 true** ⇒ **⑥ 的"必须同时断言 `typeof()`"是对的** |
> | `var_to_bytes` / `bytes_to_var` | `9007199254740993` **逐位精确往返** ⇒ **⑥ 的二进制契约成立** |
> | **本上界** | **本轮没能证伪它** —— 而**第一次尝试是错的**：我用"每元素一个残留"模拟，得出"上界 < 元素种数"，看似比本条更紧；**但 A1 的累加器是每 `(机器, 元素)` 一个**（`r[m][e]`），所以本条的界**是对的**（最坏情况下每个残留都逼近 1，欠账确实可逼近 机器数×元素种数）。**那次误报在写进本文档之前被抓住 —— 记在此处提醒后来者：一个"更紧的界"往往意味着你换了模型。** |

**它还有一个诚实的物理解释**：

> **累加器就是"反应器里还没反应完的那部分"。**
> 它不是数值补丁，而是一个**真实存在的中间状态**。

（这句话要留着 —— 它让"整数化"从技术妥协变成**物理诚实**，服务 P2。）

### ③ 整数守恒判定式 —— 以及一条**必须写明**的排除项

```
对每个元素 e：
  T_end(e) = 池(e) + 在途(e) + 机器内已整数化的量(e)

  判定：  T_end(e) == T_start(e) + 净导入(e)
          ↑ 全部整数比较，无浮点容差
```

> ⚠️ **必须显式写明：累加器里的小数部分（`r[m][e]` 本身）不计入原子总量。**
>
> 因为那部分**还不是一个完整原子**，尚未从原料中被"取出"。
>
> **这条排除项如果不写，实现者会把它算进去，然后守恒式每 tick 都失败** ——
> 而那是 **T0 那 32 次假不守恒的同一类错误：判定式写错，不是代数错**。
> **故此处写成显式警告，不留给后人自己悟。**

## Edge Cases

**八条。其中五条由已落定的规则直接决定（无需再选），三条由用户拍板。**

### 由规则直接决定（5 条）

| 边界 | 行为 | 依据 |
|------|------|------|
| **整数溢出** | **上游阻塞 + 告警**（不是丢弃）；绝不回绕、绝不出现负值 | ① |
| **出现负数** | **结构上不可能** —— 池只存非负整数；任何产生负数的路径都是 bug，必须被对账拦住。**断言：任何元素计数恒 ≥ 0** | ①⑤ |
| **对账失败** | **拒绝该动作** + 进入对账锁（需玩家确认「我知道了」才能继续） | ⑤ |
| **稀疏池里的"从未出现的元素"** | 表示上「**不存在**」与「**存在且为 0**」必须**语义等价** | ②（否则相等判定会出鬼） |
| **需求小于 1/SCALE** | 累加器永远攒不够一个整原子 → **接受它**（那本来就是"还没反应完"），但 UI 必须能解释这一状态 | ② |
| **速率的【十进制意图】与它的整数表示不相等** | **这是表示误差，不是漂移** —— 例：`37 * SCALE / 100` 截断成 `387973`，它代表 **0.369999886** 而不是 0.37；跑 100 tick 会差**整整 1 个原子**（36 vs 37），而**残留 1048564 < SCALE ⇒ 一个原子都没丢**。**⇒ 纪律：速率一律以 `SCALE` 为单位的整数【直接给定】**，十进制小数只是给人看的标签 | ② + 2026-10-03 实测 |
| **物质被存入罐子** | **不算离开池** —— 罐子是池的**有界子集**（见 §Interactions 给 B6 的契约） | ⑤ + B6 的澄清 3 |

### 由用户拍板（3 条）

| # | 边界 | 决定 |
|---|------|------|
| **A** | 查一个**不存在的元素符号** | **报错并记录（fail-fast）**，且**记录须落在玩家可见的诊断面板 + 存档**（不是只写日志 —— 只写日志等于玩家永远看不到）。理由：静默返回 0 会把拼写错误变成"这个元素就是 0"，**那是最难查的一类 bug** |
| **B** | 导入数据里**原子量为 0 或缺失**（会除以 0） | **拒绝整表导入，并指出坏在哪一行**。理由：除以 0 会污染**整张**元素表，而那张表是 **8 个下游**的基座 |
| **C** | 同一 tick 内**多台机器竞争同一元素**的搬运顺序 | **允许抢料，不保证谁赢** —— 见下面的实施口径 |

> ### ⚠️ C 的实施口径（重要，必须与用户意图对齐）
> 「不保证顺序」有两种读法，**本 GDD 按 (b) 落地**：
>
> - **(a) 顺序不确定且不可复现**（真随机 / 实现相关的迭代顺序）
>   → **存档回放、故障复现、灾难诊断全部失效** —— 而"灾难可诊断"是 P1/P2 的承诺。
> - **(b) 顺序不保证谁赢**（抢料真实存在），**但由可复现的机制决定**
>   （例如每 tick 轮转起始位置，**种子写入存档**）→ 抢料的手感在，**且回放一致**。
>
> **为什么取 (b)**：**守恒与顺序无关**（⑤ 在任何顺序下都成立，安全性不受影响），
> 而 (a) 会**单方面废掉"可诊断"** —— 用一根支柱去换一个手感，代价不对等。
> **(b) 同时满足两件事：玩家会感到"这次是它先抢到的"，而开发者仍能逐帧复现。**
>
> 若这是误读、要的其实是 (a)，**请直接说** —— 那会连带影响 B16（存档）与 B10（诊断）的设计。

**⚠️ 而"版本号"在本项目里有【三个】不同的东西，不要混为一谈**（实现时实测发现）：

| 版本号 | 管什么 | 落在哪 |
|--------|--------|--------|
| `CompoundData.SCHEMA_VERSION` | **数据表**的形状（化合物 / 步骤 / 参数的字段） | 归 **A4** |

## Acceptance Criteria

**六条。每条都必须是可独立检验的 —— 不许出现"运行正常""感觉对"。**

| # | 验收项 | 怎么测 | 通过标准 |
|---|--------|--------|----------|
| **1** | **原子守恒** | 跑任意已知工艺流程，逐 tick 逐元素比对 | `T_end(e) == T_start(e) + 净导入(e)`，**全程整数比较、无容差**；且测试必须**断言累加器的小数部分未被计入**（防复现 T0 那 32 次假不守恒） |
| **2** | **溢出注入** | 人造一次溢出 | 得到**饱和 + 告警**；且**任何元素计数不得为负** |
| **3** | **序列化往返** | 池 → 存 → 读 → 池 | **值相等** 且 **`typeof()` 仍是 `INT`**（依据：实测 JSON 往返会掉精度而 `==` 会说相等 ⇒ **必须同时断言类型**）。二进制通道必须通过；**JSON 通道应作为反例测试，它必须失败** |
| **4** | **海水导入** | 用真实海水占比跑导入 | **H:O 原子比 ∈ [2.0000, 2.0012]**（实测 2.0006）；且坏数据（原子量为 0 或缺失）**必须拒绝整表并指出坏行** |
| **5** | **缺元素符号** | 查询一个不存在的符号 | **必须报错并记录**（fail-fast，不得静默返回 0） |
| **6** | **抢料可复现** | 同一存档 + 同一 tick 序列，跑两遍 | **结果逐位一致（含"谁抢到了料"）** —— 这是 Edge Case C 的 (b) 口径的可测形式 |

> **第 3 与第 6 条是这份 GDD 从实测里换来的**：
> 第 3 条来自"JSON 会静默损坏且 `==` 会说谎"；第 6 条来自"允许抢料"必须与"可诊断"共存。
> **两条都不是通用模板话，是这个项目自己的教训。**


草案方向：
- 任意一条已知工艺流程，**每 tick 原子总数恒定**，且判定走**整数比较**（无容差）
- **溢出注入测试**：人造一次溢出，必须得到**饱和 + 告警**，不得出现负值
- **序列化往返测试**：池 → 存 → 读 → 池，**值相等且 `typeof()` 仍是 `INT`**
  （依据实测：JSON 往返会掉精度**且 `==` 会说谎**，所以必须同时断言类型）
- 海水导入：**H:O 原子比 ∈ [2.0000, 2.0012]**（实测 2.0006）
